Review the current Daymark repository and implement secure authentication, user-owned data, and focused real-time synchronization.

Do not rebuild the app.
Do not replace the existing React, TypeScript, Wouter, TanStack Query, Express, database, Object Storage, or API code.
Do not convert it into a native app.

The app currently has persistent memories and photo storage, but it needs real user accounts and correct data ownership.

MAIN GOAL

Add:

1. Secure authentication
2. Persistent user sessions
3. User-specific memories and people
4. Protected routes
5. Focused real-time updates for shared and changing data
6. A complete first-time-user flow

Use Replit Auth if it is available and compatible with the current Replit project.

Do not build password authentication manually.

PHASE 1: INSPECT THE CURRENT ARCHITECTURE

Before editing, inspect:

- API server
- database schema
- generated API client
- OpenAPI specification
- current memory tables
- people tables
- future gifts tables
- object storage ACL logic
- route structure
- TanStack Query usage

Identify every table and API route that currently lacks a user ownership field.

Do not assume a fixed demo user.

Remove any logic that treats every visitor as the same account.

PHASE 2: IMPLEMENT AUTHENTICATION

Use Replit Auth where available.

Support:

- sign in
- sign out
- persistent session
- current-user endpoint
- session restoration after refresh
- authentication loading state
- unauthorized state
- protected backend endpoints
- protected frontend routes

Do not expose access tokens to localStorage unless required by the official authentication integration.

Prefer secure HTTP-only session cookies.

Add a backend endpoint such as:

GET /api/auth/user

It should return only safe profile data:

- id
- name
- email
- profile image
- created date

Never return sensitive provider tokens.

PHASE 3: ADD USER OWNERSHIP TO THE DATABASE

Add a users table if one does not already exist.

Recommended fields:

users

- id
- providerUserId
- email
- name
- avatarUrl
- createdAt
- updatedAt

Add ownerId or userId to:

- memories
- people
- futureGifts
- notifications
- collections, if present
- drafts, if present

Add indexes on frequently queried user ownership fields.

Every query must be scoped to the authenticated user.

Examples:

A user must only see:

- their memories
- their people
- their Future Gifts
- their notifications
- their uploads

Do not trust userId sent from the frontend.

Always derive the authenticated user ID from the server session.

PHASE 4: MIGRATION AND DEMO DATA

Create and run a safe database migration.

Do not delete existing demo records.

Assign current demo data to a demo or first authenticated user where appropriate.

If assigning legacy data automatically is unsafe, preserve it as seed data and explain the migration choice.

The application must continue to load after migration.

PHASE 5: PROTECT API ROUTES

Protect all user-data routes.

Require authentication for:

- creating memories
- listing memories
- reading memory details
- updating memories
- deleting memories
- people routes
- Future Gift routes
- upload URL generation
- private object retrieval
- notification routes
- shared memory actions

Return:

401 for unauthenticated requests

403 for authenticated users attempting to access another user’s resource

404 where revealing resource existence would be unsafe

Validate ownership on the server for every resource ID.

PHASE 6: OBJECT STORAGE SECURITY

Update the existing Replit Object Storage integration so uploaded photos belong to the authenticated user.

Store the authenticated user ID as the object owner in the ACL policy.

Users must not be able to retrieve another user’s private memory photos by guessing an object path.

Check:

- upload URL generation
- ACL assignment
- private object retrieval
- memory image display
- Future Gift image display

Use public visibility only for explicitly shared content.

Normal personal memories should remain private.

PHASE 8: ROUTE PROTECTION

Public routes:

- /
- /auth
- authentication callback route

Protected routes:

- /onboarding
- /home
- /wrap
- /gifts
- /gifts/:id
- /calendar
- /people
- /people/:id
- /future-gifts
- /future-gifts/new

Routing behavior:

Unauthenticated user opening a protected route:
redirect to /auth

Authenticated first-time user:
redirect to onboarding

Authenticated user who completed onboarding:
redirect to /home

Do not briefly render protected content before authentication resolves.

Add an app-level authentication loading screen.

PHASE 10: REAL-TIME SCOPE

Do not add real-time updates everywhere.

Add real-time behavior only where it creates clear value.

Real-time updates should support:

1. Shared memories
2. Future Gifts
3. Notifications
4. People and shared-memory counts
5. Newly created memories appearing in lists

Use the best real-time mechanism compatible with the current stack.

Preferred options:

- Server-Sent Events for simple server-to-client updates
- WebSockets if two-way collaboration is needed
- database-backed subscriptions if officially supported by the chosen platform

Do not poll every second.

Keep a normal REST API as the source of truth.

Real-time events should trigger TanStack Query invalidation or cache updates.

Suggested events:

memory.created
memory.updated
memory.deleted
sharedMemory.updated
futureGift.created
futureGift.unlocked
notification.created
person.updated

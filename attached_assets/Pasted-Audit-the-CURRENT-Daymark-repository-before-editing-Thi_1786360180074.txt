==================================================
PART 1 — MIGRATE DATABASE TO SUPABASE POSTGRES
==================================================

Use Supabase PostgreSQL as Daymark's production database.

IMPORTANT:

Do NOT replace Drizzle ORM.

The current database layer already uses:

drizzle-orm/node-postgres
pg Pool
DATABASE_URL

Preserve that architecture.

Change the DATABASE_URL to the Supabase Postgres connection string and migrate
all existing Drizzle schemas safely.

Do NOT introduce a second parallel database.

Supabase should become the single production Postgres database.

Preserve all tables and relationships including:

users
people
memories
memoryPeople
memoryParticipants
calendarEvents
futureGifts
notifications
connections
relationshipStreaks
streakActivities
scheduledMessages
memoryDrops
memoryShareLinks
dailyPrompts
promptResponses

Before migration:

1. inventory all current schema
2. generate migration
3. back up existing data
4. apply migrations to Supabase
5. verify row counts
6. verify foreign keys
7. verify indexes
8. run the full application against Supabase

Do not lose existing users or memories.

==================================================
PART 2 — SUPABASE REALTIME
==================================================

Daymark already uses SSE.

Keep SSE for server-driven application events if useful.

Add Supabase Realtime only where it improves reliability and multi-instance
deployment.

Good candidates:

notifications
connections
Memory Drops
Daylink updates
shared-memory updates
scheduled-message arrival

Do NOT create duplicate event delivery.

Choose one source of truth for each event category.

Preferred architecture:

database = Supabase Postgres
auth = Clerk
ORM = Drizzle
server API = Express
realtime = Supabase Realtime and/or SSE with clear boundaries
files = current Object Storage unless intentionally migrated later

If keeping SSE:

make it work safely across multiple server instances, preferably using
Supabase Postgres events or another shared transport rather than only
in-memory client maps.

PART 3 — SUPABASE SECURITY
==================================================

Because Clerk remains the auth provider:

do not switch to Supabase Auth.

Continue using Clerk authentication.

Map Clerk user IDs to Daymark internal users.

All Express routes must still enforce ownership server-side.

If any Supabase client-side table access is introduced:

Never expose unrestricted tables through the anon key.

Sensitive tables include:

memories
people
scheduledMessages
memoryDrops
futureGifts
connections
relationshipStreaks
notifications

Prefer server-mediated access for private Daymark data.
